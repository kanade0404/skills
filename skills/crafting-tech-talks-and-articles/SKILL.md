# Crafting Tech Talks and Articles

> **規律**: 紙面を作り始める前に、コアメッセージ・ターゲット・アウトラインを先に固める。"ちゃんと伝わる" かどうかは書く前に決まっている。
> **出典**: yoshiko「伝わる発信のつくりかた」(Zennfes 2026)。本スキルはこの発表の思考フレームを skill 化したもの。

登壇・記事・寄稿など「誰かに何かを伝える」発信を、聞き手／読み手が迷子にならない形に組み立てるためのスキル。いきなりスライドや本文を書き始めると情報過多・話の迷子・時間オーバーになりやすい。**ネタ → 構成 → 紙面** の順で、上流（何を／誰に）を固めてから下流（どう見せる）に落とす。

これは「正解のある手順」ではなく **判断のフレーム**。状況により重みは変わるので、各 Step は検討ポイントとして使い、機械的に全項目を埋めない。

---

## いつ使うか / 使わない場面

起動する（口語の揺れ含む）:

- 「登壇資料つくりたい」「発表スライド作って」「LT のスライド」
- 「発表の構成考えて」「勉強会で何話そう」「カンファレンスのネタが決まらない」「CFP 出したい」
- 「技術記事書きたい」「Zenn / Qiita の記事の構成どうしよう」「会社のテックブログ書く」
- 「このスライド情報過多で伝わらない」「発表が時間内に収まらない」「記事がわかりにくいと言われた」
- 既存の発表資料・記事ドラフトのレビュー／構成立て直し

起動しない → 別スキルへ:

- **ADR・設計判断の記録** → `adr-writer`（社内向け・決定の記録）
- **調査レポート / リサーチ成果物** → `research-practices`
- **PRD・プロダクト要求・機能仕様** → `product-discovery`
- 純粋なコード実装・バグ修正・PR 本文（発信コンテンツではない）

境界: 本スキルは **社外／コミュニティ向けの発表・記事** が対象。社内設計ドキュメントや要求仕様は上記の専用スキルに渡す。同じ「文章を書く」でも、成果物が登壇・記事・寄稿なら本スキル。

## ワークフロー

進め方はチェックリスト。Step 1〜2（上流）を飛ばして Step 3 から始めない。

- [ ] Step 1: ネタを固める（コアメッセージ × ターゲット）
- [ ] Step 2: 構成を組む（洗い出し → アウトライン → リハで調整）
- [ ] Step 3: 紙面に落とす（スライド or 記事で分岐）

### Step 1 — ネタを固める

**コアメッセージ** と **ターゲット** の 2 つをはっきりさせる。これが曖昧なまま先に進まない。

- **コアメッセージ** =「発信を見た人に持ち帰ってもらいたいことを、ひとことでいうと何？」
- **ターゲット** =「今回発信する内容はどんな人に向けたもの？」（ジュニア／ミドル／ベテラン？ 特定の職種・レイヤー？ 特定技術の利用者？）

どちらか片方が決まっていれば、もう片方を連想して埋める（双方向）:

- **コアメッセージ起点**: 「このメッセージが一番刺さるのは誰か」を連想 → ターゲットを脳内に据える。コアメッセージ自体は変えずに、用語の補足・例の選び方など **伝え方をチューニング** する。
  - 例: 初心者にも読んでほしい技術解説 → この用語には補足を入れる
  - 例: 社内向けで実感を持ってほしい → 架空例でなく社内の実例を入れる
- **ターゲット起点**（イベント登壇・媒体寄稿・書籍など、自分以外が企画する場に持ち込む場合に有効）: その場のターゲット層・イベントのタイトル／コンセプト・参加者の期待から、響く難易度・抽象度を考え、コアメッセージを連想する。完全に逆算するのではなく **自分の中の「これ話せそう」を固める手がかり** として使う。

実際は一方通行ではなく、コアメッセージ ↔ ターゲットを **相互にぐるぐる深める**。

**例外 — 発信に別の目的がある場合**: 目的が「誰かに何かを伝える」以外（採用マーケ・知名度向上・ブランディング・PV など）なら、その目的を達成できる角度から構成を考える。例: 知名度を上げたい → 網羅的に技術アピールできる連載構成。

→ AskUserQuestion を使ってよい場面: コアメッセージとターゲットのどちらも本人の中で曖昧なとき、または発信の目的（伝達か／別目的か）が判然としないとき。

### Step 2 — 構成を組む

> **今日のコアメッセージ（このスキルで一番持ち帰ってほしいこと）: 情報伝達はアウトラインが命。**

1. **話したいことを洗い出す**: 最初からスラスラ書けないので、思いついたことを単語でもいいからワードクラウド的にばーっとメモる。組み立ては後。
2. **アウトラインを考える**: 見出しを並べて構造化する。2 つの基準で点検する:
   - ★ **同じ階層の見出しは同じ水準**（粒度・抽象度を揃える）
   - ★ **見出しの並びを読み流すだけで発信内容が伝わるか？**
3. **よく使う構成テンプレから選ぶ**（下表）。
4. **リハで調整**（登壇の場合）: 一度口に出して喋り、セクションごとに所要時間の目安を計る。構造が明瞭だと時間の再配分も楽。同僚・友達に聞いてもらえるとモチベ・フィードバックが得られる。

#### よく使う構成

| 型 | 流れ |
|---|---|
| **説明系** | 今日話すこと → 前提 → トピック1（説明＋事例/具体例）→ トピック2（説明＋事例/具体例）→ まとめ |
| **課題解決系** | 今日話すこと → 前提（★手法に関わるので重要）→ 課題 → 解決手法（説明／なぜ選んだか／事例）→ 結果（解決できたか／良かった点／悪かった点）→ まとめ |
| **実践共有系** | 何について共有するか → ステップ1 → ステップ2 → ステップ3 → アウトプット・結果 |

### Step 3 — 紙面に落とす

アウトラインが固まっていれば、紙面はそれ通りに作るだけ。**成果物の種類で分岐する**:

- 成果物が **スライド** → 「スライドの紙面 Tips」へ
- 成果物が **記事**（Zenn / Qiita / ブログ等）→ 「記事の紙面 Tips」へ

両方作る場合は、同じアウトラインから順に両方を適用する。

#### スライドの紙面 Tips

1. **目次をセクション代わりに使う**: 目次を中扉として各セクション冒頭に挟むと、今どこを話しているか伝わる。各スライドに見出しをちゃんと入れ、見出しだけ読み流しても流れがわかるように。
2. **下のほうに重要な文字を入れない**: 会場では前の人の頭で下部が見えない。重要情報は上半分〜真ん中に。下部はページ番号・補足など見えなくても困らないものに。
3. **見た目（誰でも読みやすく、Web と同じ）**:
   - フォントサイズ: 大きく。目安「スライド10枚／発表20分／フォントサイズ30pt」、「聴衆の最年長者の年齢 ÷ 2 = 最小フォントサイズ」などの提言あり（ref: Stanford GSB "10 steps to perfect your startup pitch"）。
   - コントラスト: 濃い色で。基準は WCAG。大きい文字なら基準は少し下がる。薄い色を使いたいなら大きく太く（ref: WCAG 2.1 Contrast Minimum）。
4. **書いてある文章をそのまま読み上げない**: 全文読むと聞いてもらえず読まれる。とはいえ後から資料単体で見て伝わる程度の文章は残す。→ **コアな内容のみ載せ**、話すときは表現を崩したり口頭だけの内容を足す。
5. **サンプルコード**: コードは相当簡単でないと初見では理解できない。4 行程度＋丁寧な解説に絞る。シンタックスハイライトは必ず入れる（SlidesCodeHighlighter が便利: https://romannurik.github.io/SlidesCodeHighlighter/ ）。

#### 記事の紙面 Tips

1. **PC とスマホ両方で見る**: 同じ文章でもスマホでは段落が長く・改行位置も変わる。PC で書き終えてからスマホで見ると印象が変わる（紙に印刷すると誤植に気付ける感覚に近い）。違和感のある表現を直し、段落を区切る／まとめるで、全体が短くまとまった印象に整える。
2. **記法を適切に使う**: 特に Zenn は独自記法（`:::message` / `:::message alert` / `:::details` / ファイル名付きコードブロック など）があるので、適切なものを選ぶと見た目もセマンティクスも上がる。公式の Markdown 記法一覧を一度眺めておく。

#### 紙面共通 — AI 文体を消す

ドラフトに AI を使ってもよいが、**最後は自分の言葉でリライト**する。AI 感丸出しだと内容が良くても文体がノイズになる。`tropes.md` や `stop-slop` のような AI 文体サンプル集を眺めて癖を掴むと気付けるようになる。

## 心構え

> **準備は真摯に、発信は気楽に。**

ここまで丁寧にやると発信のハードルが上がって見えるが、本番は気楽でいい。みんなそんなに真剣に見ていないし、話す側がガチガチだと聞く側も疲れる。**準備（Step 1〜3）には手をかけ、発信そのものは肩の力を抜く。**

## 出力フォーマット

ユーザの段階に応じて、必要な層だけ返す（全部を一度に押し付けない）:

```
## コアメッセージ
<ひとことで持ち帰ってほしいこと>

## ターゲット
<どんな人向けか + 伝え方のチューニング方針>
（発信の目的が伝達以外なら: 目的 + 角度）

## アウトライン
<見出しの並び。同階層は同水準。見出しだけで流れが伝わるか自己点検済み>
（構成型: 説明系 / 課題解決系 / 実践共有系 のどれか）

## 紙面メモ
<スライド or 記事 の該当 Tips から、今回特に効くものを抜粋>

## 次アクション
<リハで計る / スマホで確認 / AI 文体リライト など>
```

## このスキルがやらないこと

- **社内設計ドキュメントは作らない**: ADR は `adr-writer`、PRD は `product-discovery`、調査レポートは `research-practices`。
- **デザイン・作図の代行はしない**: 紙面 Tips は方針まで。実際のスライドデザインや画像生成は範囲外。
- **コンテンツの中身（技術的正しさ）は保証しない**: 構成・伝え方の支援であり、技術的事実確認は発信者の責務。
- **AI に丸投げした文体をそのまま通さない**: 最後のリライトは本人の声で行う前提。
