# prune-comments

コメントは、コードを読んでも分からないことを書くためにある。名前や型、すぐ下のコードから分かることを書いたコメントは、読む手間を増やすだけでなく、コードが変わると嘘になる。このスキルは、そうしたコメントを消すか、意味のある内容に書き直す。

docstring を減らすことが目的ではない。リンターが docstring を求めるなら docstring は残し、中身を意味のあるものにする。

## 対象

- 引数があればそのファイルやディレクトリ。なければ作業ツリーで変更したファイル（`git diff --name-only HEAD` と `git ls-files --others --exclude-standard`）。利用者が「全部」と言ったら、リポジトリで管理しているファイルすべて
- コメントの書ける設定ファイル（YAML、TOML、CI の定義など）も含める
- 上流から写したコードや生成したコード、ベンダリングしたディレクトリは除く。リポジトリにその一覧（例: `tools/vendored.json`、リンターの exclude）があれば従う

## 残すコメント

コードからは分からないことを書いたもの。

- 理由や制約: そう書いた理由、別の書き方をしない理由
  - `# 依存は全セッション・全エージェントで共有するので、別のプロセスが先に入れ終えていることがある。`
  - `# glob.glob の root_dir は 3.10 からなので、相対の glob は Path.glob で展開する。`
- 外の仕様: ファイル形式、プロトコル、マジックナンバーの意味
  - `# git の記録でシンボリックリンクを表すモード。`（`_SYMLINK_MODE = "120000"` の意味）
  - `# 出力は「<mode> <object> <stage>\t<path>」を NUL で区切ったもの。`
- 抑止の理由: リンターや型チェックを止めた理由（`# ruff: ignore[...] - 理由`、設定ファイルでルールを外した理由）
- 契約: 呼び出し側が知るべき戻り値、例外、副作用、終了コード
  - `Returns: 成功なら 0、写せなければ 1、引数の誤りなら 2。`
- 使い方: モジュールやスクリプトの使い方、設定の選ばれ方の順番

## 消すか書き直すコメント

### 1. 名前やコードの言い換え

名前、型、すぐ下の1行を読めば分かることだけを書いたもの。

| 悪い例                                       | 理由                                       |
| -------------------------------------------- | ------------------------------------------ |
| `def run(...)` の `"""フックを1回実行する."""` | 関数名の言い換え                           |
| `def parse_json(...)` の `"""JSON を読む."""`  | 関数名の言い換え                           |
| `class Message` の `"""1件の指摘."""`          | クラス名の言い換え                         |
| `Returns: 終了コード。` `Returns: 環境変数。`  | 戻り値の型と名前から分かる                 |
| `# bun のバージョン表記(例: 1.4.2)。`         | すぐ下の正規表現から分かる                 |
| `// ルールは関数か、linter を持つオブジェクト。` | すぐ下の型ガードをそのまま日本語にしただけ |
| `"""Lint のテスト."""`（`test_lint.py`）       | ファイル名の言い換え                       |

### 2. 機械的な修正で意味が崩れたもの

リンターや整形ツールに合わせた結果、読めなくなったもの。例えば ruff の D403 は、関数の docstring の最初の単語を大文字にさせる。日本語の文の先頭に識別子があると、識別子が別の名前になる。

- `"""Directory に依存が入っているかを判定する."""`（引数 `directory` が `Directory` になった）
- `"""Source にある spec.path のスキルを…"""`（引数 `source`）

識別子を大文字にして直さない。文の先頭を日本語にするか、`kernel_runner.ts` のように記号を含む語で始めて、ルールの対象から外れる形にする。

D403 はモジュールとクラスの docstring を対象にしない。`"""Textlint の依存を…"""` や `"""Kernel ランナーに…"""` のように、ルールに合わせたつもりで大文字にしたものも、元の表記に戻すか書き直す。ルールが何を求めるかは、推測せずに小さなファイルで確かめる。

### 3. 雛形の残りとコメントアウトしたコード

- 雛形やジェネレーターが入れた `# Optional: ...`、`# See https://... for available options`
- コメントアウトしたコードや設定（`# paths:`、`# claude_args: ...`）。必要なら履歴から戻せる

### 4. コードと食い違うもの

コメントの内容がコードと合わないもの。消さずに、reproduce-bug スキルの手順で再現してから利用者に報告し、コードとコメントのどちらに合わせるかを決めてもらう。コードに合わせてコメントを直すとき、リンターがその書き方を許さなければ（例: ruff は、関数自身が送出しない例外を Raises に書かせない）、その旨も伝える。

### 5. 同じ内容の重複

複数の関数に同じ docstring が付いている（`main` と `run` が両方「コマンドライン引数で実行する.」など）か、同じ説明が離れた場所に2回ある。役割の違いを書くか、片方に寄せる。

## 書き直し方

1. コードから分からないことがあるか考える。あれば、それを書く
   - `class Message: """1件の指摘."""` → `"""kernel ランナーが返した指摘 1 件. severity は 1 = warning、2 = error、3 = info."""`
   - `def run(...): """フックを1回実行する."""` → `"""フックの入力と環境変数から、出力する内容を決める. テストから直接呼べるよう、入出力を引数と戻り値にしている."""`
2. 書くことがなく、コメントが任意なら消す
3. 書くことがなく、リンターが docstring や Returns 節を求めるなら、呼び出し側に役立つ事実（値の範囲、None になる条件、副作用、どこに詳細があるか）を探して書く。それでも見つからなければ、ルールを外すかを利用者に聞く。勝手にルールを外さない
4. コメントを直すためにコードを変えない（名前を変えると分かりやすくなる場合は、提案にとどめる）

同じ規約のコメントが並ぶファイルでは、周りと書き方（文体、句点、言語）をそろえる。

## 手順

1. 対象のファイルからコメントと docstring を一覧にする（`git grep -n` で `#`、`//`、`/*`、`"""` などを探す）。一覧は省略せずにすべて見る
2. 1件ずつ、上の分類に当てはめて「残す」「消す」「書き直す」を決める
3. 変更する。コメント以外の行は変えない
4. リポジトリの検査（リンター、型チェック、テスト）を動かし、通ることを確かめる
5. 見直しを受ける（次の節）
6. 利用者に、消した件数と書き直した件数、ルールを外す提案があればその理由を伝える

## 見直し

コメントの良し悪しは書いた本人には判断しにくい。変更のあとは、作業の文脈を持たない別のエージェント（サブエージェント）か利用者に、差分を見直してもらう。見直す人には次を渡す。

- このスキルの「残すコメント」「消すか書き直すコメント」「書き直し方」の節
- `git diff` の差分

見直す人は、変更したコメントごとに次を確かめる。

- 消したコメントに、コードから分からない情報が含まれていなかったか
- 書き直したコメントが、コードと食い違っていないか
- 書き直したコメントが、まだ言い換えにとどまっていないか
- 変更しなかったコメントに、消すか書き直すべきものが残っていないか
- 変更しなかったコメントが、コードと食い違っていないか

指摘があれば直し、もう一度検査を動かす。コードレビューの依頼でこのスキルを使うときは、変更せずに、上の観点で見つけたものを指摘として返す。
