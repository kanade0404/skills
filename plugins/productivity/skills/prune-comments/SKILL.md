# prune-comments

コメントは検査されないので、コードが変わると嘘になる。コードに書けることはコードで書き、コメントは決まった例外だけに残す。消すかどうかの判断は、作業の文脈を持たないサブエージェントに任せる。書いた本人は、自分の書いたコメントを残す理由を見つけてしまう。

## 範囲

- 引数（$ARGUMENTS）があれば、そのファイルやディレクトリ
- 引数が「全部」なら、`git ls-files` の全ファイル
- 引数がなければ、既定のブランチとの差分（作業ツリーを含む）

どの場合も、上流から写したコードや生成したコードは除く。リポジトリにその一覧（例: `tools/vendored.json` の destination、リンターの exclude）があれば従う。範囲は、ファイルの一覧として書き出しておく。

## 手順

1. このスキルのディレクトリにある `references/comment-killer.md` を読み、その全文と範囲のファイルの一覧を渡して、汎用のサブエージェントを起こす。内容を要約したり、言い換えたりしない
2. サブエージェントの報告と `git diff` を検める
   - 次の変更は差し戻す: コメント以外のコードの変更、範囲の外の変更、例外の一覧に当たるコメントの削除
   - 例外に当たるとして残したものは、根拠が確かなときだけ認める。根拠が弱ければ消す
   - 報告に、範囲の外の箇所や実在しない箇所が含まれていれば、変更を戻し、誤りを伝えて1回だけやり直させる。2回目も誤っていれば、そこで止めて利用者に伝える
3. リポジトリの検査（リンター、型検査、テスト）を動かす。リンターがコメントを求めて落ちたら、コメントを書き足さずに利用者へ伝え、ルールを外すかを聞く
4. 表すべき制約として報告されたものは、いちばん安く表せる方法（テスト、型、lint）を提案し、利用者の同意を待つ。同意があれば表す。コードとの食い違いとして報告されたものは、reproduce-bug スキルの手順で再現してから報告する
5. `MUST KILL` の箇所は、残った作業として利用者に伝える。利用者に頼まれたときだけ直す
6. 次を報告する: 消したコメントの数、差し戻したもの、やり直しの有無、`MUST KILL` の一覧、表すべき制約と提案、食い違い、検査の結果

## 出典
