# persist-lesson

教訓を仕組みにするときは、置き場所を思いつきで決めない。置き場所を決める事実を先に確かめ、根拠を示して提案する。

## 手順

### 1. 何が失敗したかを、作業の題材から切り離して書く

教訓は、いま扱っている題材（コメントの整理、textlint など）の形をしていることが多い。題材ではなく、失敗した振る舞いそのものを書く。

- 悪い例は、作業の題材に寄せた書き方: コメントとコードが食い違ったら、テストで再現する
- 良い例は、失敗した振る舞いの書き方: 不具合を事実として報告する前に、再現していなかった

### 2. 置き場所を決める事実を確かめる

提案の前に、次を読む。分からないものは推測で埋めない。

- 仕組みを置く先は誰が、どこで使うか（リポジトリの README、配布先のエージェントの一覧）
- 利用者が記録した決定（ADR、引き継ぎ資料、設計の文書）
- 似た問題を解いた前例。前例の理由が書かれていなければ、利用者に聞く。理由を推測して根拠に使わない

利用者の方針として、常に効かせる決まり（rules、CLAUDE.md や AGENTS.md への決まりの追記）は使わない。仕組みは次のどちらかにする。

- 決定的なハーネス: フックや lint など、機械的に検査して守らせるもの。決まりを文脈に渡すだけのフックは、検査ではないのでハーネスに当たらない
- スキル: 決まった状況で読まれる手順

### 3. 教訓を分けて、それぞれ機械的に検査できるかを考える

- 常に守るべき短い決まりと、状況が来たときの長い手順に分ける
- それぞれについて、守られたかを機械的に検査できるかを考える。できるならハーネスに、できないならスキルにする
- 検査できない決まりをフックで文脈に渡すことは、2 の方針で除外されている

### 4. 根拠を示して提案する

- それぞれの主張に、確かめたことか推測かを付ける
- 利用者しか知らない事実で答えが決まるなら、その1点だけを聞く
- 結論は1つにする。選択肢を並べて利用者に選ばせるのは、事実が足りないときだけにする

### 5. 「なぜ？」と聞かれたら

理由を聞かれたのは、根拠を確かめられているということで、別の答えを求められているわけではない。

- 手元の根拠をそのまま示す
- 根拠が弱ければ、弱いと認め、何を確かめれば決まるかを示す
- 新しい事実が出ていないのに、反対の結論に乗り換えない

### 6. 仕組みにしたら

- スキルなら、利用者の依頼の言い回しや作業の場面で読まれるよう、説明文に具体的な引き金を書く
- 実際に読まれるかは、確かめるまで推測として扱い、報告にもそう書く

## 例

このスキル自体が、次のやりとりから生まれた。

1. 「不具合を確かめずに報告した」という教訓を、作業中だった prune-comments スキルの一節として書いた（題材に寄せた）
2. 指摘されて `~/.claude/CLAUDE.md` を提案した。このリポジトリが Codex や Cursor でも使うスキルの置き場だと README にあるのに、確かめていなかった
3. 「なぜ？」と聞かれるたびに、SessionStart フック、スキル、評価を作ってから決める、と結論を変えた。新しい事実は出ていなかった
4. 前例（文章の規約を SessionStart で渡している）の理由と、ADR の「決定的なハーネス」の意味を利用者に聞いて、ようやく決まった。「再現したか」は機械で検査できないので、スキル（reproduce-bug）にした

2 の段階で README と前例を読み、前例の理由と ADR の意味を聞いていれば、1回のやりとりで決まっていた。
