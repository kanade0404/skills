# reproduce-bug

コードを読んだだけの判断や、ほかのエージェントの指摘は推測にすぎない。不具合として報告するのは、再現してからにする。報告では、何を根拠にしたかを必ず書く。

## 手順

1. 疑いを、期待する動作と実際の動作の形で書き出す。期待する動作の根拠（docstring、コメント、README、仕様、利用者の説明）も控えておく
2. 失敗するテストを書く
   - 期待する動作を期待値にする。いまの動作に合わせない
   - 既存のテストの書き方（ファイルの置き場所、fixture、偽のコマンドや本物の依存の使い分け）に合わせる
   - 失敗の条件は、できるだけ小さく作る
3. テストを動かし、失敗することを確かめる。トレースバックを見て、失敗の原因が疑った箇所にあることも確かめる。テストの準備の誤りで失敗していないかを見る
4. テストを書けないとき（外部のサービス、手元にない環境など）だけ、実際にコマンドを動かして再現する。その理由も報告に書く
5. 再現できなければ、不具合とは報告しない。確かめた内容を添えて、疑いが外れたか、再現できなかったと伝える
6. 利用者に報告する
   - 根拠: コードを読んだだけか、テストで再現したか、手で動かして再現したか
   - 再現の結果: 失敗したテストの名前と、エラーの要点
   - 確かめていないこと: 同じ原因で起きると思われるが、動かしていない箇所
7. コードを直す前に、利用者の同意を得る。コードとコメント（文書）のどちらに合わせるかも、利用者が決める
8. 直したら、2 で書いたテストが通ることと、リポジトリの検査がすべて通ることを確かめる

## 例

モジュールの docstring には「フックの失敗でエージェントの作業を止めないよう、どの経路でも終了コード 0 で終える」とあった。しかし `run` は `TextlintError` しか捕まえず、依存を置けないときの `OSError` で異常終了していた。

- 悪い進め方: 見直し役のエージェントの指摘を、そのまま不具合として報告した。根拠を聞かれて、手で1回動かしただけで済ませた
- 良い進め方: 依存の置き場所の親をファイルにして `OSError` を起こすテストを、既存の `TestRun` の書き方で3つのモジュールに足した。3件とも失敗し、例外が `ensure_installed` から出ていることをトレースバックで確かめた。報告して同意を得てから `OSError` も捕まえるように直し、テストが通ることを確かめた
