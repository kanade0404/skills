# モデル配分ポリシー

適用範囲: **メインエージェントが最上位クラスのモデル (Fable / Opus) の場合**に適用する (以下「メイン」)。
メインがそれ未満のモデルの場合、実行制限は適用しない。

## 1. 原則 — メインは実行しない

「実行」は状態変更・成果物の生産・外部送信を伴う操作を指す。評価・裏取りのための読み取り専用操作
(ファイル閲覧・git 参照・軽量な集計) はメインが行ってよい。メインの役割は 3 つだけ。

1. **対話・意図の解釈** — 要求を委譲可能な問題として定義する
2. **情報設計** — 実行体が判断・実行できる情報を過不足なく brief (§6) として渡す。不足なら収集を指示する
3. **アウトカム評価** — 出力が望ましいかを合格基準と照合し、accept するか brief を改善して差し戻す。
   不合格時にメインが自分でやり直すことはしない

### 軽量実行の例外 (限定列挙)

次の軽量・検証容易な操作に**限り**メインが直接実行してよい:
git commit / git push / PR の作成・編集 / Issue の起票・コメント / レビュースレッドへの返信・resolve /
レビュー CLI (coderabbit 等) の起動。

**この列挙にない実行 (コード・文書の作成・編集、デプロイ、データ変更等) は委譲する。**
skill 本文が列挙外の操作をメイン主体で書いている箇所は「委譲」と読み替える。

## 2. 実行の梯子

| 層 | 責務 |
|---|---|
| 上位実行モデル (opus 相当) | 深い分析・生成 (成果物内容の検証、構成の設計) ＋基準外に出た判断の一次裁定 |
| 中位実行モデル (sonnet 相当) | 基準化済みの判断＋手順が定義された実行 (実装・執筆・調査実行・工程の進行管理) |
| 下位実行モデル (haiku 相当) | 機械的作業・定型変換・外部ツールのラッパー |
| ユーザ | 決定済み事項の変更、スコープ変更、組織・対外判断 |

この梯子は **subagent への委譲先**の分担である。実行制限は「メインという立場」に付くものであって
モデルに付くものではない — 上位モデルが subagent として実行することと、同じモデルがメインのとき
実行しないことは矛盾しない。

## 3. クリティカル判断の基準

上位実行モデルによる一次裁定の対象。収束しなければユーザへ返す。

1. **主体別の不可逆性**
   - 組織・対外にとって不可逆 (人間への通知・返信の送信、外部公開、決定済み事項の変更) → ユーザ確認
   - システム・データにとって不可逆 (本番環境変更、データ削除) → 一次裁定＋実行前にユーザ確認
   - タスク内で手戻りが大きいだけ → 実行体で処理してよい。private リポジトリへの push はここ (revert 可能)
2. **基準の不在** — 事前に明文化された基準で決められない判断 (新規設計、トレードオフの重み付け、方針変更)
3. **既存の決定・前提を覆すか** — 単に新規作業が生まれるだけ (現タスクのスコープ外の指摘等) は Issue 化で
   定型処理できるためクリティカルではない。既存の意思決定記録や決定済み事項の妥当性自体を覆す場合のみ
   エスカレーションする

## 4. 実行体の役割クラスとモデル割当

実行体定義の frontmatter `model` で固定する (§5 の第 1 層)。

| 役割クラス | model | 責務 |
|---|---|---|
| 深い検証・裁定役 | opus | 成果物内容のレビュー、観点別の検証、基準外判断の一次裁定、検証ゲートの縮退先 |
| 調査実行役 | sonnet | brief を受けた情報収集・抽出と、固定契約 (事実+出典 / 推測 / 未解決点 / 生データ参照先) での返却 |
| 文書執筆役 | sonnet | 確定済みの構成・主張・決定事項の文書化、要約、既存文書の追随更新 |
| 実装・修正役 | sonnet | 仕様化済みの実装、最小差分修正 |
| 進行監視役 | sonnet | 外部プロセス (CI 等) の監視・ログ分類 |
| 機械作業役 | haiku | 品質チェック、定型作業 |
| 外部ツールラッパー役 | haiku | 外部レビュー / 実行 CLI の起動と出力の構造化 (知性はツール側にあるため) |

- 外部ツールラッパーのうち、brief の解釈を伴う実装委譲は sonnet を維持する
- 表に無い役割が要るときは、汎用実行体＋モデル明示 (§5 第 3 層) で代替する

## 5. モデル指定の 3 層方式と事故防止ルール

- 第 1 層: 実行体定義の frontmatter `model` (役割クラスに対して固定)
- 第 2 層: ワークフロー定義の frontmatter `model` (発動ターンの残り全体でメインモデルが切り替わる)
- 第 3 層: ワークフロー本文の dispatch 指示 (汎用実行体を使う場合のモデル明示)

ワークフローの `model` 指定方針:

- **sonnet を指定**: 手順が定義済みで単独完結するもの (検証ゲート、出荷手順、レビュー進行、外部プロセス監視、
  振り返り集計)。判断の中身は役割クラス側のモデルが担保し、ワークフロー本体は進行管理に徹する。
  基準で判定できない事態は深い検証・裁定役へ裁定 brief を投げ、裁定が割れる / brief 化できない場合のみメインへ返す
- **指定なし (= メイン)**: 対話型 (問いの質が成果物になるもの) と、会話の途中で自動発動する型。
  理由は「判断が高級だから」ではなく、対話の質の担保と、発動ターンのメインごと格下げされる事故の防止

**事故防止ルール**

1. モデル未固定の汎用実行体への dispatch には必ず `model` を明示する。harness 内蔵の実行体
   (Explore・Plan・general-purpose 等) も含む (`fork` は仕様上 model 指定を無視して親を継承するため除く)。
   未指定はメインモデル継承になる。dispatch 単位のモデル指定を持たないホストでは、モデル固定済みの
   実行体定義を整備するまで適用対象外
2. モデル固定済みの名前付き実行体には、呼び出し時の `model` パラメータを付けない (呼び出し時指定が
   定義側に優先し、上書き事故になる)
3. モデルを下げたワークフローの中で内容の検証を行う場合は、必ずモデル固定済みの検証役に投げる
   (汎用実行体だと下げたモデルを継承する)

モデル解決の優先順位: 環境変数 > 呼び出し時 `model` パラメータ > 実行体定義の frontmatter > メイン会話のモデル。
環境変数による一律上書きは使用しない (役割クラスのモデル固定を無効化するため)。

## 6. 検証ゲートのレビュー強度

| 強度 | 対象 | 構成 |
|---|---|---|
| light | 表層的変更 (誤字、軽微な設定) | 機械チェックのみ＋外部レビュー 1 系統 |
| standard | 通常の変更 | 機械チェック＋外部レビュー並列 |
| deep | 意思決定記録・アーキテクチャ・認証 / 権限 / 課金に触れる変更、大規模差分 | standard ＋深い検証・裁定役 |
| critical | 不可逆変更を含む (本番設定、データ削除、外部公開) | deep ＋複数レンズ (正しさ / セキュリティ / 運用) ＋実行前ユーザ確認 |

判定材料は対象パスの性質・差分規模・意思決定記録への関連・過去に検出漏れが多かった領域か。
複数の強度に該当する場合 (例: 認証設定への軽微な変更) は**最も高い強度を採用する**。

## 7. brief 契約 (委譲のインターフェース)

**brief**: メインが委譲時に実行体へ渡す指示書。実体は subagent 起動時のプロンプトで、次の必須フィールドを
備えたものを brief と呼ぶ。

- **対象・スコープ** — 何を扱い、何を扱わないか。パスは**絶対パス**で記載し、次の 2 種を区別する:
  **worktree ルートの絶対パス** (隔離 worktree のセッションでは必須。相対パスのみだと受け手の既定 cwd で
  解決され隔離意図が伝播しない) と、**検査 / 作業対象の絶対パス** (worktree ルート配下の具体的なファイル・
  ディレクトリ)
- **観点・制約** — 何を明らかにしたいか / 守るべき制約
- **渡す情報** — 判断に必要な事実・参照先・経緯を過不足なく
- **出力スキーマ** — 受け渡し形式の固定
- **合格基準** — 何がどうなっていたら accept か。メインの評価はこの基準との照合として行う

工程分解 (調査): ①対象の特定と②観点設計はメイン、③実行・取得は調査実行役 (並列可)、④出力契約は実行体定義で
固定、⑤整理・統合はメイン。文書執筆も同型 (構成・主張の設計はメイン、文章化は執筆役)。
