# Problem Solving (Pólya の 4 段階法)

> 出典: George Pólya, *How to Solve It* (邦訳: 柿内賢信訳『いかにして問題をとくか』丸善出版)。数学教育のために書かれたが、内容はドメインに依存しない汎用の問題解決法として広く引用される。

なぜ必要か: 難しい・曖昧な問題に直面したとき、いきなり手を動かす（試行錯誤で実装し始める）と、問題の理解が浅いまま計画のない実装を繰り返し、行き詰まりを行き詰まりのまま放置しやすい。この 4 段階は「理解せずに計画しない」「計画せずに実行しない」「実行して終わりにせず振り返る」という順序を強制することで、それを防ぐ。

## いつ使うか / 使わない場面

**使う** (口語表現含む):

- 「この問題どう解けばいい」「アプローチが思いつかない」「何から手をつけていいかわからない」
- 「行き詰まった」「詰まった」「堂々巡りしている」
- バグの原因が特定できていない・再現条件はあるが原因仮説が立たない
- 複数の実装方針が考えられ、どれを取るか整理したい（ただし対象がソフトウェア設計そのものなら `design` を優先）
- 「一旦立ち止まって整理したい」「力任せにやる前に考えたい」
- 解答・実装が出た後に「これで合ってるか」「検算して」「他のやり方もあるか」

**使わない** (該当スキルに委ねる):

- ソフトウェアの構造選択・I/O 境界・依存方向の検討 → `design`
- 実装のテスト駆動サイクル・リファクタリングの分割 → `tdd` / `tidy-first`
- 既存ドキュメント・ドメイン用語との整合性チェック → `grill-with-docs`
- 文献調査・技術選定のためのリサーチ → `research-practices`
- 単純な typo 修正・自明な 1 行変更 → 直接編集（4 段階を回すコストが見合わない）

## ワークフロー

### Step 1 — 問題を理解する (Understand the Problem)

計画を立てる前に、次を**言葉にして**確認する（頭の中だけで済ませない。曖昧なまま次に進まない）:

- 未知のもの（求めたい結果）は何か。既知のデータは何か。条件は何か
- 条件は未知のものを定めるのに十分か。不十分か、余剰か、矛盾しているか
- 問題を図・記号・具体例で書き表せるか

ここで解像度が上がらない・答えられない項目があるなら、それが論点。ユーザーへの確認は `AskUserQuestion` で 1 回にまとめる（往復を増やさない）。

詳細な自問リストは `references/polya-checklist.md` の「問題を理解すること」を参照。

### Step 2 — 計画をたてる (Devise a Plan)

- 似た問題を見たことがないか。同じ問題を少し違う形で見たことがないか
- 似た問題で使った結果・方法をそのまま使えないか
- 問題をいい換えられないか。もっとやさしい関連問題、もっと特殊な問題、一部分だけを解く問題に分解できないか
- データ・条件をすべて使っているか。使っていないものがあれば、それは何のためにあるか

複数案が出たら、**採用案 1 つ + 却下した代替案とその理由**を最低 1 つ書く。代替案が 1 つも出ないなら検討が浅い（見たことのある問題への機械的な当てはめで終わっていないか疑う）。

詳細な自問リストは `references/polya-checklist.md` の「計画をたてること」を参照。

### Step 3 — 計画を実行する (Carry Out the Plan)

- 各段階を実行するたびに、その段階が正しいと確認できるか検証する（最後まで実行してからまとめて検証しない）
- 検証できない段階が出たら、そこで Step 1 / Step 2 に戻る（分からないまま先に進まない）

### Step 4 — 振り返ってみる (Look Back)

実行して終わりにしない。得られた結果に対して:

- 結果を試せるか。別の方法で確かめられるか（検算・別ルートでの再導出・テスト実行）
- 結果や方法を一目で（別の一貫した仕方で）捉え直せるか
- この結果や方法は、他の問題にも応用できるか

Look Back を省略すると、たまたま通っただけの解法・偶然動いただけの修正を「解けた」と誤認しやすい。ソフトウェアの文脈では、ここが変更後のテスト実行・別ケースでの再確認・PR での検証観点の言語化に対応する。

## 孤立した問題は subagent / multi-agent パイプラインに委譲できる

再現条件が明確なバグ・独立したアルゴリズム問題など、対話を必要とせず単発で完結する問題は、`problem-solver` subagent (`subagents/problem-solver.md`) に Agent ツール経由で dispatch できる。同じ 4 段階を、白紙のコンテキストで一気通貫に走らせ、理解・計画・実行・振り返りを構造化して返す。メインセッションでの対話的な整理が要る問題（要件が動く、ユーザー確認が要る）は本スキルをそのまま使う。

より高難度・高リスクで、1 エージェントの一発判断に委ねたくない問題は `scripts/four-step-pipeline.workflow.js` を使う（Workflow ツールが使える環境限定）。単一 subagent との違いは Step 2 と Step 4 の分解にある：

- **Step 2 (計画)**: 複数の切り口 (`planAngles`) で候補プランを並列生成し、審判役のエージェントが 1 案を採用/合成し、却下した候補とその理由を明示する（Pólya が要求する「代替案を検討したか」を構造として強制する）
- **Step 4 (振り返り)**: 複数の独立した検証方法 (`verifyMethods`) で並列に結果を検算し、その全結果を踏まえて 1 つの結論に統合する（「別の方法で確かめられるか」を、同一エージェントの自己採点ではなく別エージェントでの再検証にする）

呼び出し方:

```javascript
Workflow({
  scriptPath: "skills/problem-solving/scripts/four-step-pipeline.workflow.js",
  args: { problem: "<完全に条件が確定した問題文>" }  // planAngles / verifyMethods は省略可（既定値あり）
})
```

`problem` は事前にすべて条件が確定している必要がある（パイプライン実行中に人間へ聞き返すことはできない）。曖昧さが残る問題は先に本スキルの Step 1 を対話で済ませてから渡す。

## 出力フォーマット

ユーザーへの報告（4 段階を経たことが分かる構造にする）:

```markdown
## Problem Solving

### 理解
- 未知のもの: ...
- 既知のデータ: ...
- 条件: ...

### 計画
- 採用案: ...
- 却下した代替案: <案> — <却下理由>

### 実行
- <実施内容 / 各段階の検証結果>

### 振り返り
- 検証方法: <テスト実行 / 別ルートでの再確認 等>
- 他への応用可能性: <あれば>
```

## このスキルがやらないこと

- **特定領域の実装手順**: アルゴリズムの実装コード自体・ソフトウェア設計の決定は生成しない。4 段階の思考の型を提供するのみで、中身は `design` / `tdd` 等、または直接編集に委ねる
- **恒久ドキュメントの生成**: 4 段階の検討過程を永続ファイルとして残すことはしない（`design` の scratchpad 方針と同様、必要なら会話内かユーザー指定の一時ファイルに留める）
- **既存ドキュメント・ドメインモデルとの整合性検証**: `grill-with-docs` の担当
- **文献・先行事例の調査**: `research-practices` の担当
