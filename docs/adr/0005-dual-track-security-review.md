# セキュリティレビューを CodeRabbit と Claude Code Actions の両系統に持たせる

Status: accepted (2026-08-29)

Driver: [-ilities 1 可監査性・回復可能性](0009-ility-priority-order.md) (検出が単一点に依存しない
こと)。同 4 のレイテンシを明示的に捨てることで払える冗長である。用語は
[CONTEXT.md](../../CONTEXT.md) に従う。

## Context

PR の機械レビューは 2 系統ある。CodeRabbit は line-level のコード品質・バグ・セキュリティ。
Claude Code Actions は仕様適合 (AC ↔ 証拠の照合)・アーキテクチャ・適合度関数・セキュリティ。

このパイプラインでは実装者も LLM (Codex) で、レビュアーも LLM である。同種の見落としが起きうる
構成になっている。加えて人間の承認ゲートは merge の 1 点しかない
([ADR 0004](0004-two-human-approval-gates.md)) ため、機械レビューが取りこぼしたものは全て、
その 1 点に集まる。

観点を系統ごとに排他分担するのが素直な設計だが、セキュリティは他の観点と性質が違う。命名の悪さや
設計の歪みは見落としても後から直せるのに対し、脆弱性は merge されて稼働した時点で外部に露出する。
見落としの代償が非対称であり、shift-left の原則からも、merge 前に検出するほど安い。

## Decision

観点の分担を「排他」ではなく「セキュリティのみ重複」とする。

- **セキュリティ**: CodeRabbit と Claude Code Actions の **両系統が担う**。重複を許す。
- **line-level のコード品質・バグ**: CodeRabbit の専任。
- **仕様適合 (AC ↔ 証拠の照合)・アーキテクチャ・適合度関数**: Claude Code Actions の専任。

## Considered Options

- **観点の完全分担 (セキュリティも片系統に寄せる)** — 分担は「担当していない側は見ない」構造を
  作る。担当系統がセキュリティを取りこぼすと、そのまま merge ゲートまで到達し、人間 1 点で
  受け止めることになる。他観点なら許容できるが、セキュリティは代償が非対称なので、重複のコストを
  払う方を選ぶ。却下。
- **片系統のみ (CodeRabbit だけ / Claude Code Actions だけ)** — CodeRabbit だけでは仕様適合と
  適合度関数のレビューが無人になり、証明義務 (AC ↔ 証拠の照合) を機械で確認する経路が消える。
  Claude Code Actions だけでは、差分全行に機械的に当たる line-level の網羅性が落ちる。却下。
- **人間のセキュリティレビューを 3 点目の承認ゲートにする** — ゲート数の決定
  ([ADR 0004](0004-two-human-approval-gates.md)) と正面から衝突する。クラウド完結の価値を落とす。
  却下。

## Consequences

### Positive

- セキュリティ検出が単一障害点を持たない。片系統の設定ミス・レート制限・サービス障害でも、検出が
  ゼロにはならない。
- 専任観点 (line-level 品質、仕様適合・アーキ・適合度関数) は重複しないため、そこのレビューコスト
  と指摘の重複は増えない。冗長化のコストをセキュリティ観点だけに局所化できている。

### Negative

- **同一箇所に二重の指摘が出る**。Codex が同じ問題を 2 回修正しようとする無駄が生じる。重複の集約
  機構は置かず、同一 PR 内で Codex が解決する運用コストとして受け入れる。
- PR あたりのレビュー実行コストとレイテンシが増える。これは -ilities 4 (レイテンシを捨てる) の
  直接の帰結であり、この決定が成立するのは優先順を先に固定したから
  ([ADR 0009](0009-ility-priority-order.md))。
- **「両方が見ているから安全」という誤った安心が生まれうる**。LLM 2 系統は独立事象ではない。
  新種の脆弱性や、文脈依存の認可バグのように「そもそもモデルが見立てを持てない」種類の欠陥は、
  両系統で相関して見落とされる。冗長化が下げるのは独立な見落としの確率だけで、相関する見落としは
  残る。この残余リスクは merge の人間ゲートが負う — 機械レビューが 2 系統通ったことは、merge の
  根拠にはならない。
- レビュー系統が 2 つとも外部サービスなので、外部依存が減らない。片方を落とす選択肢を、この決定
  は自ら塞いでいる。

### Neutral

- 系統の追加・入替は two-way door。観点の分担表は運用実績 (どちらがどの種類を先に見つけたか) で
  見直せる。
