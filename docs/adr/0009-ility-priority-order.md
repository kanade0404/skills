# -ilities の優先順を 可監査性・回復可能性 > 有界性 > 並行性 > レイテンシ とする

Status: accepted (2026-08-29)

Driver: 本 ADR 自身が下流の全決定の Driver である。用語は [CONTEXT.md](../../CONTEXT.md) に従う。

## Context

このパイプラインは、人間が張り付かない前提で LLM (Fable / Codex / 機械レビュー) が仕様と実装を
動かす。この構成での失敗の主要な形はプロセスのクラッシュではなく、**間違ったまま進む / 静かに
止まる / 無限に回る** の 3 つである。いずれも、外から見えなければ何時間でも継続しうる。

アーキテクチャ特性は互いに競合する。速くしようとすれば状態をローカルに持つことになり、並列度を
上げれば書き手が増えて一貫性の保証が難しくなる。優先順を先に固定しないと、下流の各決定が別々の
暗黙の順序を仮定して下され、後から矛盾が露見する。実際、設計レビューの round 1 から 3 にかけて、
優先順が言語化されていない間は同じ論点 (速度と可監査性のどちらを採るか) が繰り返し再燃した。

体制の制約として、運用は solo で、常時監視する人間はいない。異常に気づくのは事後である。

## Decision

アーキテクチャ特性の優先順を、以下に固定する。競合したら常に上位を採る。

1. **可監査性・回復可能性** — 全状態が GitHub 上で人間に見え、どの構成要素が死んでも GitHub から
   再構築できる。**例外領域を作らない**。
2. **有界性** — 全てのループ・全ての待機・全てのコストに数値の上限がある。上限を強制する主体自身
   も有界であること。
3. **並行性** — 上 2 つを害さない範囲でのみ追求する。
4. **レイテンシ** (およびマルチテナント効率) — **明示的に捨てる**。

この順序が下流の全決定の Driver である。各 ADR は自身の Driver がどの -ility かを明記する。

### 下流への効き方

- [ADR 0007](0007-github-as-sole-durable-state.md) 耐久状態を GitHub のみに — 1 の直接の帰結。
- [ADR 0008](0008-github-conformist.md) GitHub Conformist — 1 (人間が見ている面が真実) と維持コスト。
- [ADR 0003](0003-two-layer-task-and-implementation-issues.md) 二層 issue — 分解結果を GitHub 上に
  出すのが 1、実装 issue 数の上限が 2。
- [ADR 0004](0004-two-human-approval-gates.md) 承認ゲート 2 点 — 仕様書き換えを人間に留めるのが 1、
  ゲートの待ち行列に上限を置くのが 2。
- [ADR 0006](0006-four-way-spec-rejection-sum-type.md) 差し戻し 4 分類 — ルーティング可能性が 1、
  閉路の辺に上限を置けるようにするのが 2。
- [ADR 0005](0005-dual-track-security-review.md) セキュリティ二重化 — 4 を捨てることで払える冗長。
- 未起票の下流決定 (書き込み権威の lease、各種 cap、状態の定期読み直し、token の分離) も、同じ
  順序を Driver とする。

## Considered Options

- **レイテンシを 2 位に置く** — レイテンシを買う手段は、状態をローカルに持つ (1 に違反) か、状態の
  読み直しを減らす (取りこぼしが復元できなくなり 1 に違反) しかない。人間が張り付かない運用で、
  反映が数分早いことに価値が無い。却下。
- **並行性を 1・2 より上に置く** — 並行性を最優先にすると複数の書き手を許すことになり、状態の
  一貫性の保証が実行体どうしの合意に移る。GitHub 上で人間に見える形の権威が失われ、1 が崩れる。
  却下。
- **優先順を決めず、決定ごとに個別に判断する** — 下流の決定が互いに別々の暗黙の順序を仮定し、
  矛盾が後から露見する。設計レビューで実際に観測された失敗モードそのもの。却下。
- **順序ではなく数値の予算 (可用性 SLO 等) で表す** — 予算は測定を前提とするため、測定基盤を先に
  作ることになる。順序は測定なしで意思決定に使える。solo 運用の初期段階では順序が適切。却下。

## Consequences

### Positive

- 下流の決定で「どちらを採るか」を毎回議論しなくてよい。各 ADR は Driver を 1 行で書ける。
- 「速いが見えない」設計案を、詳細に立ち入る前に機械的に落とせる。
- 優先順が明文化されているため、後から順序自体を議論の対象にできる (暗黙のままだとできない)。

### Negative

- **遅い**。全ての判定が GitHub の読み直しを経るため、変更の反映は秒ではなく分の単位になる。
- **GitHub API の消費が多い**。レート制限が実質的なスループット上限になり、API 予算の管理という
  運用作業が新たに発生する。
- 並行性が 3 位なので、安全性が確認できない限り並列度を上げられない。スループットは意図的に低い
  水準に留まる。速くしたいという要求に対して、この順序は構造的に「ノー」を返し続ける。
- **順序が固定されているため、「ここだけ速くしたい」という後からの要求は原則として却下される**。
  例外を作れば 1 の「例外領域ゼロ」が崩れ、可監査性は例外の数だけ穴が開く。柔軟性を意図的に捨てて
  いる。
- 1 位が可監査性なので、機械が読むためだけの状態も人間が読む面に出る。人間にとっての情報密度は
  下がる。

### Neutral

- 順序の変更は、下流の ADR 群を連鎖的に見直すことを意味する。one-way door に近い。
