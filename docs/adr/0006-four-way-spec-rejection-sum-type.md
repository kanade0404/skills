# 差し戻しを 4 分類の sum type にする

Status: accepted (2026-08-29)

Driver: [-ilities 2 有界性](0009-ility-priority-order.md) (差し戻しはループを閉じる辺なので分類と
上限が無いと発散する)、同 1 可監査性 (分類が機械可読でないとルーティングできない)。用語は
[CONTEXT.md](../../CONTEXT.md) に従う。

## Context

差し戻しは、仕様の欠陥を理由にタスクを Fable の再検討へ返すことである。発生源は Codex (分解時・
実装時) とレビュー (PR 審査時) の両方にあり、どちらから出ても基準は同一でなければならない
— 基準が発生源ごとに違えば、同じ欠陥が経路によって差し戻されたりされなかったりする。

差し戻しは、人間の承認ゲート 2 (差し戻し再検討) を起動する唯一の経路でもある
([ADR 0004](0004-two-human-approval-gates.md))。したがって「何が差し戻しか」が曖昧だと、人間の
待ち行列に何でも流れ込み、ゲートを 2 点に絞った意味が失われる。

また、差し戻し → 仕様修正 → 再着手 はパイプラインのイベントグラフに閉路を作る。閉路を持つ系で
-ilities 2 (有界性) を満たすには、その辺を通る回数に上限を置く必要があり、上限を置くには「何が
その辺を通ったか」を数えられる形にしなければならない。

## Decision

差し戻しの理由を、閉じた 4 値の sum type とする。

1. **AC の矛盾** — AC 同士が両立しない。
2. **制約 / Non-goals との抵触** — AC を満たすと制約または Non-goals を破る。
3. **垂直スライス不成立** — 単独で merge して壊れない最小単位に切れない。
4. **infeasible** — AC は無矛盾だが技術的に実現不能。

この 4 値以外を理由とする差し戻しは受理しない。とりわけ **実装手段・内部設計・テスト設計の困難は
差し戻し対象ではなく、Codex の裁量内**である。レビューのコード / 実装レベルの指摘も差し戻しでは
なく、Codex が同一 PR で修正する。

## Considered Options

- **3 分類 (infeasible を持たない)** — AC が無矛盾で、かつ技術的に実現不能な場合の出口が消える。
  Codex は差し戻す先を持たず、実装を試み続けて試行上限 (cap) に到達し、「理由の分からない cap
  超過」として滞留する。infeasible は「仕様側が動かない限り解けない」という判定であり、要求の
  所有者に返す必要がある。cap 超過という無情報な終端を、この種の失敗の墓場にしないために 4 つ目
  を置く。却下。
- **自由記述 (理由を文章で書かせる)** — 再検討で何を書き直すか (AC を直すのか、Non-goals を
  広げるのか、切り方を変えるのか、スコープを諦めるのか) が機械的に決まらず、ルーティングできない。
  分類ごとの発生数も数えられないため、仕様品質の劣化を検知する手段が失われる。却下。
- **レビュー観点ごとにさらに細分化する** — 分類の目的は再検討で「何を書き直すか」を一意にする
  ことで、その目的には 4 値で足りる。細分化は判定の揺れと、どの値に入れるかの議論を増やすだけ。
  却下。

## Consequences

### Positive

- 差し戻しの受理判定が機械化できる。分類外の理由 (実装がつらい、テストが書きにくい) は Codex に
  差し戻され、人間の待ち行列には入らない。ゲート 2 点の設計が守られる。
- 分類ごとの発生数が仕様品質のシグナルになる。1 が多ければ AC の書き方、3 が多ければタスクの切り
  方に問題があると読める。
- infeasible が明示的な出口を持つため、実現不能なタスクが試行上限まで資源を焼いてから無情報に
  停止する経路を塞げる。

### Negative

- **4 値のどれにも綺麗に当てはまらない欠陥が実際に出たとき、無理に既存の値へ押し込む圧力が働く**。
  分類の意味が運用の中で劣化していく。分類の追加は sum type の拡張であり、判定コード・集計・
  再検討手順の全てに波及するため、ADR の改訂を要する重い変更になる。
- 「実装手段の困難は差し戻さない」を強制するため、実際には仕様が悪いのに Codex が黙って苦しみ
  続けるケースが起こりうる。仕様の欠陥と実装の困難の境界判定を Codex に委ねており、その判定の
  正しさを機械で検証する手段は無い。
- 分類 3 (垂直スライス不成立) のように、機械的に再分解できそうに見えるケースでも必ず人間ゲートを
  起動する。再分解の自動化は仕様の書き換えに接近するため、ゲート 2 点の決定
  ([ADR 0004](0004-two-human-approval-gates.md)) に従って人間を通す側に倒している。人間の
  ラウンドトリップが、避けられたかもしれないケースでも発生する。
- GitHub には sum type を表現する型が無いため、実体はラベルまたはコメント規約という弱い表現に
  なる ([ADR 0008](0008-github-conformist.md) の代償)。網羅性と排他性の検証は自前のチェックに残る。

### Neutral

- 分類値は機械可読な列挙として単一のファイルに持ち、受理判定・集計・再検討手順がそれを共有する。
