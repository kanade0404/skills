# 人間の承認ゲートを merge と差し戻し再検討の 2 点に置く

Status: accepted (2026-08-29)

Driver: [-ilities 1 可監査性・回復可能性](0009-ility-priority-order.md) (仕様が無人で書き換わらない
こと)、同 2 有界性 (ゲートは待ち行列なので滞留に上限が要る)。用語は [CONTEXT.md](../../CONTEXT.md)
に従う。

## Context

このパイプラインの価値の一部は「人間が張り付かなくても進むこと」そのものにある。ゲートを増やす
ほど、その価値は目減りする。

一方で、無人で起きてはいけない変更が 2 種類ある。

1. **main への反映** — merge された内容がプロダクトの現実になる。
2. **仕様の書き換え** — AC・Non-goals・制約は要求の表現であり、これが変わることは「何を作るか」が
   変わること。実装者側 (Codex) やレビュー側の都合で無人に書き換わってはいけない。

GitHub 側の機構として、branch protection + ruleset により merge を人間の明示操作に留めることが
できる。App に merge 系権限を与えないことと合わせて、これは規約ではなく機構として強制できる。
一方、仕様の書き換えを機構で止める手段は GitHub には無く、経路の設計で担保するしかない。

[差し戻し](0006-four-way-spec-rejection-sum-type.md) は、仕様の欠陥を理由にタスクを Fable の再検討
へ返すことであり、定義上、仕様の書き換えを要求する唯一の経路である。

## Decision

人間の承認ゲートを **2 点だけ**置く。

1. **merge** — branch protection + ruleset で機構的に強制する。
2. **差し戻し時の再検討** — 差し戻しの通知を受けて、人間が Fable セッションで AC・Non-goals・制約
   を見直す。

それ以外はゲートにしない。タスクの issue 起票は Fable との対話内の合意で代替する。着手可
(依存タスクが全て決着) の判定は機械判定で、Codex への投入は自動で始まる。

## Considered Options

- **merge のみの 1 点** — 差し戻しが自動で仕様を書き直すことになる。要求の解釈が無人で変わったまま
  実装が進み、merge ゲートではそれが見えない (diff に出るのはコードだけで、AC がいつ・なぜ変わった
  かは現れない)。仕様書き換えの無人化そのもの。却下。
- **3 点以上 (issue 起票・着手にもゲートを置く)** — 着手可の判定は「依存が全て決着したか」という
  機械判定で、人間が足せる情報が無い。ゲートを置けばクラウド完結の価値が落ち、かつ人間待ちの
  待ち行列が 1 本増えて滞留の総量が増える (-ilities 2 に対して不利)。却下。
- **差し戻しの自動再検討 (Fable が無人で AC を書き直す)** — 上と同じ理由に加え、差し戻し 4 分類の
  うち infeasible は「AC 自体を諦めるか、スコープを切り直すか」という要求所有者の判断であり、
  代行できる性質のものではない。却下。

## Consequences

### Positive

- 無人で変わってはいけない 2 つ (main の内容、仕様の内容) が、両方とも人間の明示操作を通る。
- merge ゲートは branch protection という機構で強制でき、実装の善意に依存しない。
- ゲートが 2 点しかないので、パイプラインが「今どの人間待ちで止まっているか」が単純に表現できる。

### Negative

- **人間が 2 本の待ち行列のボトルネックになる**。滞留に数値上限を置き、超過を可視化しないと、
  「人間待ちで止まった状態」を正常な待機と誤認したままパイプラインが静止する。しかも上限超過で
  取れる行動はリマインドの再通知までで、デフォルト前進はしない — 人間ゲートの意思決定を代行しない
  以上、待ちは伸びうる。これは有界性の例外ではなく「有界なのは通知の間隔だけ」という限界である。
- 差し戻しが必ず人間の再検討を経るため、AC の些細な言い回しの矛盾でも人間のラウンドトリップが
  発生する。差し戻し基準を狭く定義すること
  ([ADR 0006](0006-four-way-spec-rejection-sum-type.md)) が前提条件になっている。
- 機械レビューは承認ゲートではないので、CodeRabbit / Claude Code Actions が通ったことは merge の
  根拠にならない。「AC ↔ 証拠の照合」の最終判定の責任は merge する人間に残る
  ([ADR 0005](0005-dual-track-security-review.md) の残余リスクもここに集まる)。
- 着手を自動にしたことで、人間が「これは今やらなくていい」と思っているタスクも、依存が解けた瞬間
  に走り出す。止めたい場合は依存または状態の側で表現しなければならない。

### Neutral

- ゲートを減らす方向 (merge のみ) への変更は two-way door。増やす方向は運用負荷として即座に現れる
  ため、変更の是非は運用実績で判断できる。

## Erratum (2026-08-30)

**本 ADR の本文は変更しない。** 「merge が機構で強制できる」という事実の記述に誤りがあったので、
ここに訂正を記す。訂正の対象は次の 3 箇所である。

- Context の「**App に merge 系権限を与えないことと合わせて、これは規約ではなく機構として強制できる**」
- Decision 1 の「**merge — branch protection + ruleset で機構的に強制する**」
- Positive の「**merge ゲートは branch protection という機構で強制でき、実装の善意に依存しない**」

いずれも「機構」の中身を、実際より強く述べている。

- **GitHub は「merge だけを除外する」permission の粒度を持たない。** installation 全体としては、merge に
  必要な permission を持ちうる。「App に merge 系権限を与えない」という設定は存在しない。
- merge が `contents` と `pull_requests` の両方を要する見込みであることを利用して、**worker が発行する
  job token を操作の種類ごとに分割し、両方入りの token を作らない**という運用は可能である。しかしこれは
  **worker の token 発行関数が守る不変条件であって、GitHub が強制する機構ではない**。発行関数にバグが
  あれば成立しないし、merge を gate する permission の特定自体が Phase 1 の実測項目である。
- **ruleset も無条件には機構と呼べない。** master の update bypass を人間アクターに限る設定はできるが、
  **restrict-update が merge API の呼出 actor に効くかは公式の明文がなく実測待ち**であり、auto-merge は
  ruleset が再評価されないという報告がある。Decision と Positive の「branch protection + ruleset で
  機構的に」は、この実測が済むまでは確定した機構ではない。
- **現時点で機構と呼べるのは、[ADR 0015](0015-capability-broker-instead-of-container-credentials.md) が
  決めた構造** — Codex 実行コンテナが GitHub credential 自体を持たないので merge API に到達できない —
  **だけである**。ただしこれは worker 自身の侵害を覆わない。

訂正後の正しい姿 — merge を人間に限定する 3 層と、どの層が load-bearing かの書き分け (層の番号もそこで
定義する) — は [ADR 0013](0013-role-separated-tokens-and-credentials.md) の「merge を人間に限定する
3 層」に記す。**本 ADR の決定 (承認ゲートを merge と差し戻し再検討の 2 点に置く) 自体は、この訂正の影響
を受けない。** 変わったのは「その決定を何が支えているか」の説明だけである。
