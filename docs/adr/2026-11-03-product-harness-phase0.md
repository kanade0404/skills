# プロダクトハーネスの Phase 0

- 状態: 承認
- 日付: 2026-11-03

この ADR は、要件からプロダクトを自律的に作るハーネスの土台となる決定を記録する。決定 1 から 9 は、すべて利用者と合意している。合意の外で ADR の書き手が補った具体値や手段には「（提案）」と書く。提案は Phase 1 で見直す。

## 背景

ハーネスの目標は、要件を渡すと商用の品質のプロダクトを自律的に作ることにある。品質には内部の品質（コードとテスト）と外部の品質（振る舞いと性能）の両方を含む。ハーネスは自分の誤りも直す。

ハーネスは実際のプロダクトを作りながら少しずつ組み立て、このリポジトリに置く。このリポジトリは、手元では pinniped と呼び、GitHub では `kanade0404/skills` にある。対象とするプロダクトの種類は次の 4 つで、順番は決定 1 で決める。

- CLI（OS のプロファイリング）
- MCP サーバー（情報の検索）
- RAG を使う、低遅延の TTS・STS の AI エージェント
- RBAC を持つ、CRM のような Web アプリ

自律的に作らせるときの主な問題は 3 つある。1 つ目に、作る側が通ったと言っても、正しさの証拠にはならない。2 つ目に、長い作業で文脈が自動で圧縮されると、そのあとの品質が落ちる。3 つ目に、同じ誤りを何度も繰り返す。この ADR の決定は、この 3 つへの対処を中心にしている。

## 決定

### 1. プロダクトの順番

最初のプロダクトは B、2 番目は A とする。どちらも CLI（OS のプロファイリング）の枠に入る。MCP サーバー、TTS・STS のエージェント、CRM のような Web アプリは、A のあとに続く。

B は `time` コマンドを拡張したもので、macOS と Linux で動く。`/usr/bin/time -l`（macOS）と `/usr/bin/time -v`（GNU、Linux）より多くを報告する。B の名前は未定で、この ADR では `b` と仮に書く。B の要件は次のとおりとする（範囲は提案）。

- `b [オプション] -- コマンド [引数...]` の形で、コマンドを子プロセスとして実行する
- 子の終了コードをそのまま返す。シグナルで終わった子は `128 + シグナル番号` を返し、どのシグナルかを報告する
- コマンドが存在しないときは 127、実行できないときは 126 を返し、標準エラー出力に理由を 1 行で書く。子は起動しないので、計測の報告は出さない（提案）
- 経過時間、ユーザー CPU 時間、システム CPU 時間を報告する
- ピーク RSS をバイト単位にそろえて報告する。macOS の `ru_maxrss` はバイト、Linux はキロバイトなので、単位を変換する
- rusage の残りの項目を報告する。マイナーとメジャーのページフォルト、自発的と非自発的のコンテキストスイッチ、ブロックの入出力、受けたシグナルの数を含む
- 子ごとの内訳を報告する。直接の子は `wait4` の値を使う。孫以降は 10 ms 間隔のサンプリングで取り、近似値であることを出力に明記する（提案）
- サンプリングの間隔より短く終わった子孫は、合計には入るが内訳に出ないことがある。この制約を help に書く（提案）
- 出力は人が読む形式と `--json` を持ち、JSON にはスキーマのバージョンを入れる。`-o ファイル` で出力先を変える
- その OS で取れない項目は 0 ではなく null（人向けの出力では `n/a`）にする。Linux で常に 0 を返す `ru_nsignals` なども、取れない項目として扱う
- B が足す時間のオーバーヘッドは、経過時間の 2% か 5 ms の大きい方以下にする（提案）

2 番目の A は、Linux 向けに strace を eBPF で置き換えるもので、Rust と aya で書く。

### 2. 評価関数を中心の資産にし、評価関数そのものを検証する

評価関数を、ハーネスの中心の資産とする。評価関数そのものも検証の対象にする。失敗するところを見たことがない評価関数は、何も証明しない。評価関数は次の方法で検証する。

- mutation testing で、プロダクトのコードに入れた変異を評価関数とテストが見つけるか確かめる
- わざとずるをした実装を用意し、評価関数が不合格にすることを確かめる。出力を固定した実装や、sleep で時間を水増しした実装などを使う
- 答えが分かっている負荷で確かめる。決まった量の CPU スピン、決まった量のメモリ確保、決まった回数の fork などを使う
- macOS の `/usr/bin/time -l` と、GNU（Linux）の `/usr/bin/time -v` を相手に差分テストをする
- メタモルフィックな関係を確かめる。たとえば仕事の量を 2 倍にすると、CPU 時間もおよそ 2 倍になる
- プロパティベースのテストを使う
- 障害を注入する。子が kill される、シグナルを受ける、コマンドが存在しない、といった場合を含む
- 同じ負荷を繰り返し実行し、値の安定性とばらつきを確かめる
- 生成側が一度も見ないホールドアウトのケース集を持つ

ホールドアウトのケース集は、このリポジトリとは別の非公開リポジトリに置き、評価の CI ジョブだけが取得する（提案）。生成側が読めるリポジトリに置くと、生成側が見ないことを保証できない。評価では、生成されたプロダクトをホールドアウトのない別のジョブで実行し、入力と結果だけを受け渡す（提案）。同じジョブで動かすと、プロダクトのコードがホールドアウトを読めてしまう。

別のジョブに分けても、プロダクトは実行時に `argv`、環境変数、CI の特徴を調べて、ホールドアウトの入力にだけ正しい値を返せる。これを防ぐため、評価には次の境界を置く（提案）。

- ホールドアウトの入力は、評価ジョブが秘密の seed と評価ごとの nonce から実行時に生成する。seed は評価側の secret に置き、生成側とプロダクトには渡さない。nonce は評価ごとに新しく作り、同じ seed と nonce の組を 2 回使わない。固定の入力は使わない
- 期待値は、評価側だけが持つ隠したオラクル（参照実装や、答えが分かっている負荷）で計算する。プロダクトの出力を期待値の根拠にしない
- 入力に依存して振る舞いを変える実装を、決定 2 の「わざとずるをした実装」に含める。判定は 2 通りで行う。1 つ目に、各出力を隠したオラクルの期待値と比べる。2 つ目に、同じ論理入力を、環境変数、argv の形、CI の特徴の違う条件で実行して出力を比べる。比べる対象は、終了コード、JSON のスキーマ、`null` と `n/a` の扱いなど、条件で変わらない項目とする。計測値は、決定 9 の差分テストと同じ許容誤差で比べる。許容誤差を広げる変更は、評価側の変更として人が判断する。どちらかで食い違えば不合格にする。入力が違えば出力が違うのは当然なので、違う入力どうしの出力の差だけでは不合格にしない
- プロダクトを動かすジョブは、ネットワークと認証情報を持たない。ホールドアウトのリポジトリの認証情報は、プロダクトを動かすジョブに渡さない

### 3. 生成側と評価側を分ける

生成側と評価側では、文脈とプロンプトを分ける。生成側は評価関数とホールドアウトのケース集を編集しない。

この禁止は 2 段で強制する（提案）。生成側のセッションでは、評価関数の置き場所への書き込みを PreToolUse フックで拒否する。CI では、プロダクトのコードと評価関数を同じ PR で変えた変更を不合格にする。評価関数は、人がレビューする別の PR で変える。

同じ PR の変更検査だけでは、生成側の PR が評価 CI の設定を変えて検査を無効にできる。そこで、評価 CI の制御は生成側から変更できない経路に置く（提案）。評価のワークフローは、保護された base ブランチの定義だけを使い、PR が変えたワークフローでは動かさない。評価の合否は、人が管理する必須チェックとする。生成側の PR は、そのチェックの定義も、必須とする設定も変更できない。評価の実行は、ホールドアウトと同じ非公開リポジトリのジョブで行う。評価関数、ホールドアウト、評価 CI の設定の変更は、人のレビューを必須にする。具体的な設定は、workflow と GitHub の設定を正本にし、この ADR には書かない。

ハーネス自体（プロンプト、スキル、ループ）の評価と改善には、claude-api スキルの `build-eval` と `hillclimb` を使う。`build-eval` は Claude を使うアプリの評価セットを作り、`hillclimb` は既存の評価セットに対してアプリを繰り返し改善する。どちらも Claude を使うアプリ向けに作られているので、対象はハーネスであり、B の実行時の処理ではない。`hillclimb` では、ケースを train、validation、test に分けて使う。

プロダクトの性能の指標（B のオーバーヘッドなど）を改善するときは、pstack の poteto-mode にある hillclimb のプレイブック（`playbooks/hillclimb.md`）に従う。

### 4. 修正のループと段階的な引き上げ

評価関数が不合格を返したら、生成側に回数を限って修正させる。上限を超えたら、次の順に段階を上げる。回数は初期値である（提案）。

1. 同じ文脈で、最大 3 回まで修正する
2. より強いモデルか、より高い effort に切り替えて、最大 2 回まで修正する
3. 失敗の要約だけを渡した新しい文脈で、最大 2 回まで修正する
4. 人に引き継ぐ

同じ失敗が 2 回続けて同じ形で出たら、残りの回数を待たずに次の段階へ進む（提案）。

どの段階でも、テストや評価関数を弱めて通すことはしない。期待値の緩和、ケースの削除、許容誤差の拡大は、評価側の変更として人が判断する。

### 5. 学びの記録

失敗するたびに、失敗の内容、根本原因、修正をリポジトリの中の永続するログに追記する。ログは追記だけで、書き換えない。

同じパターンが繰り返されたら、スキル、ルール、評価関数のケースのどれかに昇格させる。昇格の目安は、同じ根本原因が 3 回記録されたときとする（提案）。

各セグメントの開始時に、このログを読む。ログの置き場所は `harness/learnings.md` とし、1 件ごとに日付、失敗、根本原因、修正、証拠のパスを書く（提案）。

追記: PR のレビューの指摘は、この決定に沿って `harness/review-learnings.jsonl` に記録する。機械で数えて昇格させるので、Markdown ではなく JSON Lines にした。昇格の目安は、pstack の `correct` に合わせて 2 回とし、重い指摘は 1 回でも昇格させる。手順は productivity の review-learning スキルにある。

### 6. 自動圧縮に頼らず、セグメントに分けて引き継ぐ

自動の compact のあとは品質が落ちる。そこで、長い作業は次の仕組みで進める。

- 外部の駆動役（`claude -p` か Agent SDK）が、新しい文脈のセグメントを順に実行する
- Stop フックが文脈の使用量を確かめる。使用量は、statusline の JSON の `context_window.used_percentage` か、トランスクリプトのトークン数から取る
- statusline の JSON は statusline のコマンドにだけ渡り、Stop フックの入力には含まれない。そこで、statusline のコマンドが値をセッションごとの状態ファイルに書き、Stop フックはそれを読む（提案）
- 状態ファイルには、セッション ID と、値を計算したときのトランスクリプトの最後のメッセージの ID も書く。Stop フックは、セッション ID が今のセッションと一致し、メッセージの ID がトランスクリプトの今の最後のメッセージと一致する値だけを使う（提案）
- 一致する値がないときは、トランスクリプトで代える。最後のアシスタントのメッセージの usage にある入力、キャッシュの読み書き、出力のトークン数を足し、文脈の窓の大きさで割って割合にする（提案）
- どちらの方法でも使用量が分からないときは、しきい値を超えたものとして扱い、引き継ぎを求める（提案）
- 実装の前に、statusline のコマンドと Stop フックが動く順番を実機で確かめる
- 使用量がしきい値を超えていたら、Stop フックは終了を止め、引き継ぎファイルを書くように指示する。引き継ぎファイルには、目標、現状、次の手順、未解決の失敗、証拠のパスを書く
- 駆動役が次のセグメントを始め、SessionStart フックが引き継ぎの内容を文脈に戻す
- SessionStart フックの additionalContext は 1 万文字までなので、それより長い引き継ぎはパスで参照させる
- 自動の compact は、最後の安全網としてだけ有効にしておく
- API エラーで終わったターンでは、Stop の代わりに StopFailure が動く。StopFailure は出力と終了コードが無視されるので、終了を止められない。ユーザーの割り込みやプロセスの異常終了でも、Stop は動かないことがある。そのため、Stop フックだけを引き継ぎの経路にはしない（提案）
- 回復の経路として、StopFailure と SessionEnd のフックは、副作用だけで最小のチェックポイントを `harness/state/<実行 ID>/` に書く。内容は、実行 ID、セッション ID、セグメントの番号、終了の理由、トランスクリプトのパスである。SessionEnd は時間の予算が短いので、処理は軽くする（提案）
- 外部の駆動役は、`claude -p` の終了コードと引き継ぎファイルの有無を見る。ファイルが無くチェックポイントだけがあるときは、チェックポイントとトランスクリプトからファイルを作ってから次のセグメントを始める。作れなければ人に引き継ぐ。レート制限のときは、待ってから同じセグメントを再開する（提案）

`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` は、自動圧縮のしきい値を下げることしかできない。`/clear` をプログラムから実行する方法もない。このため、文脈の入れ替えは外部の駆動役が受け持つ。

具体値は次のとおりとする（提案）。しきい値は 60% にする。引き継ぎファイルは `harness/state/<実行 ID>/handoff-<セグメントの番号>.md` に置き、git の管理から外す。1 回の実行のセグメント数は 20 までとし、超えたら人に引き継ぐ。`stop_hook_active` は、ほかの Stop フック（ja-writing の Stop フックなど）が終了を止めたときにも真になる。そのため、このフラグだけでは引き継ぎを飛ばさない。ハーネスの Stop フックは、自分が止めた回数をセッションごとの状態ファイルに持ち、2 回止めたらそれ以上は止めない。引き継ぎファイルには、実行 ID、セッション ID、セグメントの番号を書く。古い実行のファイルを取り違えないように、パスにも実行 ID とセグメントの番号を入れる。次のセグメントを始める前に、駆動役は引き継ぎファイルがあることを確かめる。あわせて、必須の項目がそろい、ID と番号が今の実行と一致することも確かめる。どれかが欠けていれば、人に引き継ぐ。

### 7. サブエージェントの方針

サブエージェントの使い方は、Anthropic の記事「[Building agents: When to fold subagents into your main agent loop](https://claude.com/ja/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)」に従う。

既定の形は、1 つのメインループとスキルの組み合わせとする。スキルは、要るときにだけ全体を読み込む（段階的な開示）。サブエージェントは、次のどれかに当たるときだけ使う。

- 文脈の肥大による性能の低下を測って確かめた
- 並行して進める作業があり、終わったら文脈を捨ててよい
- ツールの選び間違いや、システムプロンプトの指示どうしの衝突が起きている

独立した評価側は、この方針の例外として意図的に分ける。関心の分離のためで、この判断は記事の主張ではなく、このリポジトリ独自の決定とする。

この方針は、`productivity:subagent-judgment` のスキルとフックで実装する（PR #187）。

### 8. テストの環境

Linux での振る舞いは、コンテナの中で確かめる。macOS の振る舞いはコンテナでは確かめられないので、実機の Mac か、GitHub の macOS ランナーを使う。

A の eBPF は、複数のカーネルのバージョンで確かめる必要があり、コンテナでは足りない。Lima か virtme-ng の VM を使う。

### 9. B の完了の条件

B は、次の条件をすべて満たしたときに完了とする。数値はすべて初期値で、Phase 1 で見直す（提案）。

- 単体テストとプロパティベースのテストが通る。プロパティごとに、CI では 256 ケース以上を生成する
- 評価関数の検証が通る。mutation score は 80% 以上とし、ずるをした実装はすべて不合格になる
- 答えが分かっている負荷で、期待どおりの値が出る。50 回 fork する負荷では、負荷のプロセスが B の直接の子で、fork された 50 個が孫になる。各孫が 100 ms 以上生きる負荷を使う。100 ms はサンプリングの間隔の 10 倍である。このとき、内訳の孫以降の数（負荷のプロセス自身は除く）がちょうど 50 になる。
  - 256 MiB を確保して書き込む負荷では、ピーク RSS が 256 MiB 以上 288 MiB 以下になる
- 差分テストが、macOS と Linux の両方の CI で通る。CPU 時間は相手の値の ±10% か 20 ms の大きい方、ピーク RSS は ±5% か 1 MiB の大きい方の範囲に入る
- メタモルフィックなテストで、仕事の量を 2 倍にしたときの CPU 時間の比が 1.8 から 2.2 の間に入る
- 同じ負荷を 10 回実行したとき、CPU スピンの CPU 時間の変動係数が 5% 以下になる
- 障害の注入のケース（子の kill、シグナル、存在しないコマンド）で、終了コードと報告が仕様どおりになる
- 決定 1 の要件ごとに受け入れテストがあり、すべて通る。対象は次のとおりである
  - コマンドの実行と引数の受け渡し（`b [オプション] -- コマンド [引数...]`）
  - 成功時の終了コードの素通し
  - シグナルで終わった子の `128 + シグナル番号` と、シグナルの報告
  - 126 と 127 の区別、計測の報告を出さない条件
  - 経過時間、ユーザー CPU 時間、システム CPU 時間の報告
  - ピーク RSS のバイト単位への換算
  - rusage の各項目
  - 子ごとの内訳（近似であることの明記と、短く終わった子孫が内訳に出ない制約の help への記載を含む）
  - 人が読む形式の出力、`--json`（スキーマのバージョンを含む）、`-o <file>`
  - 取れない項目の `null` と `n/a` の表現
  - オーバーヘッドの上限
- lint とフォーマットの検査が警告なしで通る
- `--help` の出力と README があり、出力のすべての項目と、OS ごとに取れない項目を説明している
- リリースの範囲を満たす。GitHub Releases には、Linux の x86_64 と aarch64 向けの静的リンクのバイナリと、macOS の aarch64 向けのバイナリを置き、SHA-256 のチェックサムを添える。macOS の署名と公証、パッケージマネージャーへの登録は範囲に含めない（範囲は提案）

## 影響

### よい影響

- 評価関数が失敗するところを先に見るので、合格という結果を信用できる
- 生成側と評価側を分けるので、生成側がテストを書き換えて合格を作る道がなくなる
- 学びの記録と昇格によって、同じ誤りが次のプロダクトで繰り返されにくくなる
- セグメントに分けた引き継ぎによって、長い作業でも自動の compact の後の品質の低下を避けられる

### コストとリスク

- 評価関数とその検証を先に作るので、B の最初の動く版が出るまでの時間が延びる
- macOS のランナーは Linux より遅く、CI の時間と費用が増える。A の VM のテストも同様である
- 差分テストとばらつきの検査は、CI のランナーの負荷によって不安定になりうる。許容誤差を広げて逃げると評価が弱くなるので、不安定なケースは理由を記録して個別に扱う
- 評価側を別の文脈で動かすので、トークンの費用が増える
- 引き継ぎファイルの質が低いと、次のセグメントが状況を取り違える。引き継ぎの質そのものを `build-eval` の評価の対象に入れる必要がある
- 学びの記録が増えると、セグメントの開始時に読む量が増え、文脈を圧迫する。ログは書き換えずに残し、昇格したものをまとめた要約を別に作って、開始時にはその要約を読むといった整理が要る
- 決定 6 は、statusline の JSON の項目名や additionalContext の上限など、Claude Code の現在の仕様に依存する。仕様が変わったら見直す

## 検討した代替案

- 重いマルチエージェントの編成: 調整の費用が大きく、記事の既定（1 つのメインループ）に反するので採らない
- 自動の compact だけに頼る: compact の後に品質が落ちるので採らない
- 生成と評価を 1 つの文脈で兼ねる: 自分の出力を甘く評価し、テストを弱める誘因が残るので採らない
- LLM による採点だけで評価する: 計測値の正しさを確かめられず、評価関数の検証もできないので採らない
- A を先に作る: eBPF には VM と複数のカーネルが要り、評価関数の検証の仕組みを作る最初の題材としては費用が大きいので採らない
- `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` で圧縮を遅らせる: しきい値は下げることしかできないので採らない
- macOS もコンテナで確かめる: コンテナでは macOS のカーネルの振る舞いを再現できないので採らない

## Phase 1 の次の一手

- B の実装言語と、B のコードの置き場所（このリポジトリか、別のリポジトリか）を決める。どちらも Phase 0 では決めていない
- `harness/` の構成を決め、学びの記録（`harness/learnings.md`）と引き継ぎファイルの置き場所を作る
- 生成側より先に、B の評価関数を作る。答えが分かっている負荷、ずるをした実装、差分テストから始める
- 評価関数の検証（mutation testing と、ずるをした実装の不合格）を CI に組み込む
- ホールドアウトのケース集を、生成側から読めない場所に置く
- CI に macOS と Linux のマトリクスを用意する
- Stop フック、SessionStart フック、外部の駆動役を作り、短い作業で引き継ぎが働くことを確かめる
- 生成側が評価関数を書き換えられないことを、フックと CI で確かめる。保護の対象には、評価関数、ホールドアウト、評価の CI の設定を含める。ツールによる編集だけでなく、シェル、ファイルの移動、シンボリックリンク、PR での CI の設定の変更も拒否するか検出する
- 生成されたプロダクトを、ホールドアウトのないジョブで実行する仕組みを作る（決定 2）
- PR #187（`productivity:subagent-judgment`）を取り込む
- ハーネス自体の評価セットを `build-eval` で作り、train、validation、test に分ける
- この ADR の「（提案）」の値を、B を作りながら見直す
