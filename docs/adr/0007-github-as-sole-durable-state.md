# 耐久状態を GitHub のみに置く

Status: accepted (2026-08-29)

Driver: [-ilities 1 可監査性・回復可能性](0009-ility-priority-order.md) を「例外領域ゼロ」で満たす
こと。同 4 のレイテンシと運用効率を代償に払う。用語は [CONTEXT.md](../../CONTEXT.md) に従う。

## Context

パイプラインの構成要素 — Fable セッション、Codex を駆動する実行体、レビュー層 (Actions)、人間 —
はいずれも落ちうるか、使い捨てられる。実行体は再起動され、セッションは終了し、コンテナは破棄
される。

-ilities の最上位は可監査性・回復可能性であり、その要件は「全状態が GitHub 上で人間に見え、どの
構成要素が死んでも GitHub から再構築できる」ことである。ここで重要なのは **例外領域をゼロにする**
という条件で、状態の一部でも GitHub の外にあると、その部分だけが人間から見えず、その部分だけが
再構築できない。設計の過程で、実行体の内部状態だけが例外領域として残る案を検討したが、その一点が
可監査性と回復可能性の両方を無効化することが分かった。

GitHub 側で耐久な器として使えるものは、issue / PR / label / comment / git ref である。これらは
GitHub Conformist の方針 ([ADR 0008](0008-github-conformist.md)) により、変換せずそのまま使う。

キューについては、webhook が高速化の経路であって必須経路ではない (取りこぼしは定期的な状態の
読み直しが拾う) ため、耐久キューが買うものが無い、という事実が前提にある。

## Decision

**耐久状態は GitHub のみに置く**。issue / PR / ラベル / コメント / git ref が唯一の状態ストア
である。

実行体のメモリ・in-process キュー・worktree は **キャッシュ**であり、失われてよい。実行体は起動時
に GitHub から状態を再構築する。GitHub の外に置く永続コンポーネントを持たない。

**本 ADR の範囲は「状態がどこにあるか」に限る**。どの実行体がいつ書いてよいか — すなわち書き込み
権威 (lease) の設計 — は本 ADR では決めず、別 ADR (未起票) に委ねる。本 ADR は状態の所在を決める
だけで、並行する書き手の調停については何も主張しない。

## Considered Options

- **外部 DB (状態を専用ストアに置き、GitHub には表示用に写す)** — 状態が二重になり、必ず乖離する。
  乖離したときにどちらが正かを決める機構がさらに要る。そして人間が GitHub で見ているものが真実で
  なくなった時点で、-ilities 1 の要件そのものに違反する。却下。
- **Postgres 等の耐久キュー** — 上と同じ二重管理の問題に加えて、webhook が必須経路でない以上、
  キューの耐久性が防いでいる障害が存在しない。取りこぼしは定期の読み直しが拾う。必要が実測で
  確認された時点で足せばよい。却下。
- **ハイブリッド (進行中の一時状態だけ外部に置く)** — 「一時」の範囲が実行体の生死をまたいだ瞬間
  に例外領域になる。実行体のクラッシュはまさにその瞬間に起きるので、最も復元が必要な状況で最も
  復元できない。却下。

## Consequences

### Positive

- 実行体が全滅しても、GitHub を読めば進行が復元できる。バックアップと復旧の対象が GitHub だけに
  なる。
- 人間が見ている画面が、定義上そのまま真実である。状態を覗くための専用ツールが要らない。
- 運用しなければならない外部の永続コンポーネントがゼロ。solo 運用で維持できる。

### Negative

- **遅い**。全ての判定が GitHub の読み直しを経る。反映までの時間は秒ではなく分の単位になる。
- **GitHub API の消費が多い**。レート制限が実質的なスループット上限になる。API 消費に数値目標を
  置き、超過を検知したら周期を延ばす縮退動作が必要で、これは追加の運用作業である。
- GitHub が状態ストアとして持つ制約 — コメントの無制限成長、ラベル語彙の変更コスト、一覧のページ
  ング — を緩衝なしに直接受ける。
- **GitHub が落ちている間、パイプラインは進行できない**。可用性の上限が GitHub の可用性で決まる。
  自前の縮退運転という選択肢を、この決定は自ら放棄している。
- 機械が読むための状態も人間が読む面 (issue / コメント) に同居するため、ノイズが増える。人間に
  とっての可読性は、状態量が増えるほど下がっていく。

### Neutral

- one-way door に近い。運用開始後に外部ストアを足すと、乖離の解消コストが蓄積した状態量に比例して
  増える。
- 書き込み権威の設計 (lease) は本 ADR に依存する下流の決定であり、-ilities の同じ優先順
  ([ADR 0009](0009-ility-priority-order.md)) を Driver とする。
