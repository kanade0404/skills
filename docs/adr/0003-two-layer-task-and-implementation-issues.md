# タスクと実装 issue を二層に分ける

Status: accepted (2026-08-29)

Driver: [-ilities 1 可監査性・回復可能性](0009-ility-priority-order.md) (分解結果が人間に見えること)、
同 2 有界性 (実装 issue 数の上限)。用語は [CONTEXT.md](../../CONTEXT.md) に従う。

## Context

クラウド完結の開発パイプラインでは、仕様を詰める側 (Fable セッション) と実装する側 (Codex) が
分離している。Fable は claude.ai/code 上で仕様・AC・Non-goals・制約を決めるが、対象リポジトリの
既存コード・依存関係・テスト基盤という実装コンテキストを持たない。Codex は実装時にリポジトリを
読むので、それを持つ。「どこで作業単位を切るか」の判断材料が、両者で非対称になっている。

外部制約として、GitHub の sub-issues が GA になり、親 1 件あたり sub-issue 100 件・階層 8 段まで
を GitHub 自身がネイティブに保持する。親子関係を自前のラベル規約や本文リンクで管理する必要が
なくなった。この事実が本決定の前提であり、[ADR 0008](0008-github-conformist.md) の Conformist
方針と組み合わさって、issue 階層をそのままドメインの階層として使えるようにしている。

作業単位の分解結果をどこに置くかは、耐久状態の置き場所
([ADR 0007](0007-github-as-sole-durable-state.md)) の問題でもある。

## Decision

作業単位を二層にする。

- **タスク** = outcome 単位の親 issue。AC・Non-goals・制約を持ち、**Fable が起票する**。
  実装単位ではない。完了 = 配下の全実装 issue の決着 + 親 AC の全満たし。
- **実装 issue** = ちょうど 1 つの PR で決着する垂直スライスの sub-issue。
  **Codex がタスクを読んで分解し、起票する**。

分解の裁量は Codex にあり、Fable は実装粒度に関与しない。逆に Codex は AC・Non-goals・制約を
書き換えない (書き換えが必要なら [差し戻し](0006-four-way-spec-rejection-sum-type.md))。

## Considered Options

- **単層 (1 issue = 1 PR、Fable が実装粒度まで踏み込む)** — Fable は実装コンテキストを持たない
  ため粒度判断が推測になる。推測が外れても「差し戻し」という明示の信号にはならず、垂直スライス
  が成立しない issue が黙って流れる。加えて outcome が複数 issue に散るため、「タスク完了」の
  判定を載せる宿主が消える。却下。
- **三層 (outcome / feature / PR)** — 中間層に固有の決定が無い。AC は最上位に付き、垂直スライス
  の規準は最下位に付く。中間層は親子の同期コストと、GitHub の 8 階層制限の消費だけを足す。却下。
- **issue 外での分解 (Codex の内部計画に留め、PR だけを出す)** — 分解結果が GitHub 上に現れない
  ため、進行が人間に見えず、実行体の再起動で失われる。-ilities 1 の「例外領域ゼロ」に違反し、
  [ADR 0007](0007-github-as-sole-durable-state.md) とも矛盾する。却下。

## Consequences

### Positive

- outcome が一意の宿主 (親 issue) を持つ。完了判定の前半 (配下の全実装 issue の決着) は issue
  階層から機械的に読める。後半 (親 AC の全満たし) の最終判定は人間が merge ゲートで担う
  ([ADR 0004](0004-two-human-approval-gates.md))。
- 実装粒度の裁量が、実装コンテキストを持つ側 (Codex) に寄る。判断材料と判断権限が一致する。
- 分解結果が GitHub 上の耐久状態として残るので、実行体が死んでも復元できる。

### Negative

- **実装 issue の本文が Codex の書き込みになる**。これを後段が「指示」として読み戻すと、Codex が
  自分で書いたテキストが仕様の権威を獲得する経路 (信頼のロンダリング) が開く。実装 issue 本文は
  data として扱い、指示として使うのは親タスクから転記・検証された契約ブロックだけ、という規律で
  塞ぐ必要がある。この規律の機構化は本 ADR の範囲外 (別 ADR: 信頼境界)。
- issue の総数が増える。1 タスクあたりの実装 issue に数値上限を持たないと、分解が発散したときに
  GitHub 上の状態が爆発する。上限の設計は有界性 (-ilities 2) 側の決定に委ねる。
- GitHub の親 100 件 / 8 階層という上限を、緩衝なしに直接受ける
  ([ADR 0008](0008-github-conformist.md) の代償)。現行の運用既定値は上限のおよそ 1/5 を想定して
  いるため直近の問題ではないが、張り付いた場合の縮退動作は未設計である。
- 一つの outcome を見るのに親と子の 2 画面を行き来することになり、人間の読み取りコストが単層より
  高い。

### Neutral

- one-way door。運用開始後に層を増減すると、既存の issue 群とその参照 (依存・cap 集計) の作り直し
  になる。
